# План: SSE-стриминг транскрипции + VAD-чанкование

Дата: 2026-08-13. Статус: **VAD-чанкование реализовано** (silero-vad v5 запечён в образ, +HF-зеркало; чанкер по паузам; параметры `vad`/`chunking_strategy`; тумблер в WebUI; 4 теста на корректность таймстемпов, включая пропуск тишины). **Стриминг реализован**: `stream=true` → SSE (delta/done как у OpenAI), стрим-чанки 12 с, отмена инференса при разрыве, слот очереди на весь стрим, демо в WebUI (тумблер «Стриминг», прогрессивный текст, метрика «первый текст через X с»). Замер на файле 137 с: первый текст через 1.18 с, полный — 6.07 с. Остался только п.3 (фразовые cue для srt/vtt).
Обе фичи — уровень движка/раутов, друг друга усиливают; порядок внедрения —
сначала VAD (фундамент), потом стриминг (надстройка).

---

## 1. VAD-чанкование (silero-vad)

### Что сейчас и в чём проблема

Длинное аудио (> 25 с) режется на **жёсткие чанки по 30 с** без оглядки на
речь: граница может прийтись на середину слова (ошибки распознавания на
стыках), тишина и музыка прогоняются через модель наравне с речью (лишний
CPU + риск галлюцинаций), а субтитры наследуют грубую 30-секундную нарезку.

### Дизайн

1. **Модель**: silero-vad v5 (ONNX, ~2 МБ, MIT) — зеркалим файл в наш
   HF-репозиторий `vvpreo/gigaam-v3-onnx` рядом с остальными весами.
   Новых python-зависимостей **ноль**: onnxruntime уже в образе; пишем
   свой минимальный враппер (~100 строк, окно 32 мс/512 сэмплов,
   рекуррентное состояние) вместо pip-пакета.
2. **Новый чанкер** в `src/asr/onnx_engine.py` (заменяет `_chunk_bounds`
   для длинного аудио): VAD-проход → вероятности речи → границы пауз;
   чанки набираются до `GIGAAM_CHUNK_SEC`, но **резка только по паузам**
   (ближайшая пауза назад от лимита); участки тишины длиннее ~1–2 с
   выбрасываются целиком; хвосты < `GIGAAM_MIN_CHUNK_SEC` сливаются.
   Фолбэк: если пауз нет (непрерывная речь/шум) — старые жёсткие границы.
3. **Флаг**: `VAD_CHUNKING=true|false` (дефолт true), выключение
   возвращает текущее поведение.
4. **Бонус для субтитров**: границы cue совпадают с паузами; вместе с
   пословными таймстемпами позволяют собрать фразовые cue (отдельный
   маленький шаг в этом же этапе).

### Оценки

| Метрика | Сейчас | С VAD | Комментарий |
|---|---|---|---|
| CPU-оверхед VAD-прохода | — | ~0.3–1 % длительности аудио | silero ~200–500× реального времени на 1 потоке; для файла 137 с ≈ 0.3–0.7 с |
| Время обработки речи | 100 % | 100 % речи, **0 % тишины** | на «дырявых» записях (диктофон, звонки) выигрыш 10–40 % полного времени |
| RAM | — | +40–60 МБ | сессия silero + буферы; на фоне 2.4 ГБ незаметно |
| Образ | 733 МБ | +2 МБ | сам silero-vad |
| Качество на стыках | слова режутся | резка по паузам | главный выигрыш; плюс меньше галлюцинаций на музыке/шуме |
| Латентность первого байта | без изменений | без изменений (batch) | меняет только стриминг (ниже) |

**Трудоёмкость**: ~день (враппер + чанкер + фразовые cue + тесты на
паритет качества и на «дырявое» аудио + зеркалирование весов).

**Риски**: агрессивный VAD может выкинуть тихую речь (шёпот) — порог
вероятности делаем настраиваемым (`VAD_THRESHOLD`, дефолт 0.5) и
сверяем WER на нашем сэмпле до/после.

## 2. SSE-стриминг (`stream=true` на OpenAI-контракте)

### Что сейчас и в чём проблема

Ответ приходит только целиком: для файла в 137 с пользователь ждёт ~6 с,
для часового подкаста — ~2.5 минуты без какой-либо обратной связи.
OpenAI SDK уже умеет `stream=True` — сейчас мы параметр честно
игнорируем.

### Дизайн

1. **Движок**: вариант `transcribe_stream(audio, ...)` — генератор,
   отдающий результат **по мере готовности каждого чанка** (текст чанка +
   границы + слова). Инференс уже почанковый — по сути, превращаем
   существующий цикл в генератор; сам инференс не меняется.
2. **Раут**: при `stream=true` → `StreamingResponse`
   (`text/event-stream`), формат событий строго как у OpenAI:
   `data: {"type":"transcript.text.delta","delta":"…"}` на каждый чанк,
   в конце `data: {"type":"transcript.text.done","text":"…","usage":{…}}`.
   Инференс в thread pool, события через `asyncio.Queue` — event loop
   живой, слот очереди (429-лимит) удерживается на всё время стрима.
3. **Стрим-режим нарезки**: для стриминга уменьшать целевой чанк до
   ~10–15 с (настройка `STREAM_CHUNK_SEC`) — первое событие приходит
   раньше; с VAD-чанкованием границы остаются по паузам.
4. **WebUI**: прогрессивное дописывание текста в карточку результата.
5. Вне рамок v1: WebSocket/Realtime-протокол (живой микрофон) — отдельная
   большая задача, в план не входит.

### Оценки

| Метрика | Сейчас (batch) | Со стримингом | Комментарий |
|---|---|---|---|
| Время до **первого** текста, файл 137 с | ~6 с (весь ответ) | **~0.6–1.5 с** | первый чанк 10–15 с при ~23× реального времени |
| Время до первого текста, часовой подкаст | ~2.5 мин | **~1 с** | главный выигрыш UX |
| Полное время обработки | X | X (+1–3 % SSE-оверхед) | суммарный компьют тот же; чуть больше мелких чанков → немного больше вызовов encoder |
| Пропускная способность | — | без изменений | слот очереди держится столько же |
| RAM | — | без изменений | буферизуется только текст |
| Совместимость | stream игнорируется | OpenAI SDK `stream=True` работает | формат событий 1-в-1 с OpenAI |

**Трудоёмкость**: ~день (генератор в движке + SSE-раут + очередь/отмена
при разрыве соединения + прогрессивный WebUI + тесты на поток событий).

**Риски**: обрыв клиентского соединения посреди стрима — нужно корректно
отменять инференс (проверка `request.is_disconnected()` между чанками),
иначе зомби-задачи занимают слот.

## Порядок и связка

1. **VAD-чанкер** (день) — сразу улучшает качество стыков, субтитры и
   скорость на тишине для всех существующих запросов.
2. **Стриминг** (день) — поверх готового почанкового генератора; с VAD
   дельты приходят фразами, а не обрубками.
3. Фразовые cue srt/vtt из слов + пауз — маленький финальный штрих.

Суммарно: ~2–2.5 дня работы, +2 МБ к образу, +50 МБ RAM, регресса
скорости нет (на реальных записях — ускорение), латентность первого
результата падает на порядок.
