# Замеры на DGX Spark (GB10): GigaAM на CUDA и Whisper turbo

Дата: 2026-09-24 (faster-whisper — 2026-09-25). Железо: **DGX Spark**, NVIDIA GB10 (Grace Blackwell,
sm_121, 48 SM), 121 ГиБ единой памяти, aarch64, CUDA 13.0, драйвер 580.173,
кап клока GPU 2200 МГц. На боксе параллельно жили чужие сервисы
(faces-and-persons, ollama без загруженных моделей); во время части WS-прогонов
GigaAM шла компиляция whisper.cpp (8 потоков CPU) — на GPU-цифры не влияет,
CPU-колонки первых прогонов слегка завышены.

Стек: сервис `up-and-run-stt` из `Dockerfile.cuda` (ONNX Runtime **1.30.0**,
`onnxruntime-gpu` с PyPI, `CUDAExecutionProvider`, fp32-веса), whisper.cpp
(CUDA, `CMAKE_CUDA_ARCHITECTURES=120;121`) с `ggml-large-v3-turbo`. Скрипты —
`benchmark/streaming/`, сырые результаты — `~/code/gigam-serving/.tmp/results-*/`
на споке.

Аудио: `sample-data/Sobolev_Andrey_1_0_00-2_17.ogg` (137 с русской речи с
паузами, 16 кГц моно), одно и то же во всех сессиях; сессии стартуют со сдвигом
0.5–1.3 с.

## TL;DR

- **CUDA на Spark работает штатно**: `pip install onnxruntime-gpu==1.30.0`,
  образ на `nvidia/cuda:13.0.1-cudnn-runtime-ubuntu24.04`, никаких сборок из
  исходников. Клип 137 с — **0.53 с** (RTF 0.004, ~260× реального времени;
  на CPU i7-8750H было 6.4 с).
- **Живая диктовка GigaAM**: инференс фразы **~35 мс** (CTC) / ~30 мс (RNNT);
  задержка от конца аудио фразы до текста **p50 ≈ 0.09–0.10 с, p95 ≈ 0.15 с**,
  и она **не растёт до 20 сессий включительно** (p95 0.17 с). Пользователь видит
  текст примерно через **0.6–0.7 с после того, как замолчал**: 500 мс паузы,
  которую сервер ждёт, чтобы закрыть фразу, плюс ~0.1 с.
- **GPU при этом почти простаивает**: средняя загрузка 0–4 %, пики 15 % при 20
  сессиях. Узкое место при росте числа сессий — **CPU**, ≈ **0.1 ядра на сессию**
  (silero-VAD и лог-мел-фичи считаются на CPU): 20 сессий ≈ 2 ядра из 20.
- **Память GigaAM**: 4.0 ГиБ на весь контейнер с двумя моделями (CTC + RNNT,
  включая CUDA-контекст), RSS процесса 1.7 ГиБ в простое / 2.6 ГиБ под нагрузкой.
  От числа сессий не зависит (+2 МБ на сессию).
- **Whisper large-v3-turbo (whisper.cpp)**: окно 10 с — **~0.12 с** на запрос в
  потоке (энкодер 175 мс на холодный вызов, декод 10–12 мс greedy / 50 мс beam 5);
  6 параллельных окон по 10 с — 0.73 с суммарно, т.е. **~8 окон/с**. Для трёх
  пользователей псевдо-стриминга с тактом 0.5–1 с (3–6 окон/с) запаса хватает.
  Память 2.4 ГиБ. Русский текст с пунктуацией адекватный.
- **faster-whisper (CTranslate2, собран под sm_121)** — окно 10 с за
  **0.05–0.09 с** (11–15 окон/с), в 1.5–2 раза быстрее whisper.cpp, память
  2.7–3.5 ГиБ; батчинг окон выигрыша не даёт — энкодер насыщает GB10 одним
  окном. Рядом с LLM окно дорожает вдвое (5–7 окон/с), LLM теряет 20 % (§3.1).
- Итог: на одном GB10 и GigaAM, и Whisper turbo тянут 2–3 пользователя с большим
  запасом; GigaAM — десятки сессий. Ограничивает не GPU, а CPU и сериализация
  инференса одним воркером.

## 1. Офлайн-запросы (HTTP, клип 137 с)

Инференс сериализован локом на модель (один воркер), поэтому суммарная скорость
при параллельных запросах не растёт — запросы становятся в очередь, и RTF
каждого растёт пропорционально их числу.

| Модель | Параллельных запросов | RTF на запрос p50 / max | Суммарно ×RT | CPU avg / max |
|---|---|---|---|---|
| `v3_e2e_ctc` | 1 | 0.004 / 0.004 | 259× | 2 % |
| `v3_e2e_ctc` | 3 | 0.008 / 0.011 | 261× | 298 % / 595 % |
| `v3_e2e_ctc` | 6 | 0.013 / 0.022 | 264× | 557 % / 1107 % |
| `v3_e2e_rnnt` | 1 | 0.007 / 0.007 | 143× | 395 % / 790 % |
| `v3_e2e_rnnt` | 3 | 0.015 / 0.022 | 137× | 530 % / 1014 % |

Для сравнения CPU (i7-8750H, 6 ядер): CTC RTF 0.088, RNNT 0.111 — **ускорение
в ~20 раз** для CTC и ~16 раз для RNNT. RNNT на GPU медленнее CTC почти вдвое:
его greedy-декодер — покадровый цикл маленьких сетей, он сидит на CPU (на GPU
его съел бы оверхед запуска ядер) и грузит несколько ядер.

Где уходит время 0.53 с у CTC: VAD-проход по 137 с и лог-мел-фичи на CPU, сам
энкодер на GPU — десятки миллисекунд. Отсюда же плато ~260×: параллельные
запросы не ускоряются, потому что CPU-часть и GPU-часть идут под одним локом.

## 2. Живые сессии (WS `/stt/stream`, реальное время)

Каждая сессия льёт клип 137 с в реальном времени 100-мс кадрами; сервер сам
режет на фразы (silero-VAD, пауза 600 мс) и распознаёт каждую. Задержка
считается от момента отправки последнего сэмпла фразы до получения текста —
в ней очередь и инференс, но **не** 500 мс тишины, которые сервер оставляет в
конце фразы (их надо прибавить, чтобы получить «замолчал → увидел текст»).

| Модель | Сессий | Фраз | Overflow | Задержка p50 / p95 / max, с | Инференс p50 / p95, с | GPU avg / max | CPU avg / max | RSS max |
|---|---|---|---|---|---|---|---|---|
| CTC | 1 | 29 | 0 | 0.100 / 0.130 / 0.139 | 0.036 / 0.048 | 0 % / 7 % | 10 % / 88 % | 2.6 ГиБ |
| CTC | 3 | 87 | 0 | 0.091 / 0.148 / 0.163 | 0.035 / 0.056 | 0 % / 8 % | 30 % / 108 % | 2.6 ГиБ |
| CTC | 5 | 145 | 0 | 0.087 / 0.141 / 0.182 | 0.021 / 0.039 | 1 % / 8 % | 54 % / 134 % | 2.6 ГиБ |
| CTC | 10 | 290 | 0 | 0.096 / 0.144 / 0.195 | 0.034 / 0.053 | 2 % / 15 % | 102 % / 218 % | 2.6 ГиБ |
| CTC | 20 | 580 | 0 | 0.104 / 0.166 / 0.226 | 0.036 / 0.069 | 4 % / 13 % | 192 % / 388 % | 2.6 ГиБ |
| RNNT | 1 | 21 | 0 | 0.087 / 0.145 / 0.174 | 0.030 / 0.061 | 0 % / 8 % | 13 % / 117 % | 2.6 ГиБ |
| RNNT | 3 | 63 | 0 | 0.095 / 0.154 / 0.164 | 0.025 / 0.058 | 1 % / 7 % | 43 % / 140 % | 2.6 ГиБ |
| RNNT | 10 | 210 | 0 | 0.106 / 0.169 / 0.209 | 0.034 / 0.078 | 2 % / 15 % | 139 % / 311 % | 2.6 ГиБ |

(CPU в % от одного ядра, как в `docker stats`; 100 % = одно ядро целиком.)

Что видно:
- Задержка **плоская** от 1 до 20 сессий: инференс фразы 35 мс, фразы приходят
  раз в ~4.7 с на сессию, так что даже 20 сессий — ~4 фразы/с × 35 мс ≈ 15 %
  занятости GPU-воркера. Очередь не образуется, overflow ни разу не случился.
- **CPU растёт линейно, ≈ 10 % ядра на сессию** (VAD 0.5 % + фичи + WebSocket).
  Это и есть ограничитель: на 20 ядрах Spark потолок порядка 100–150 сессий по
  CPU, задолго до того, как упрётся GPU (см. стресс-тест ниже).
- RNNT в живом режиме не дороже CTC по задержке (фразы короткие), но ест больше
  CPU из-за декодера — при равном качестве смысла нет, при лучшем (WER 4.9 %
  против 6.2 %) — цена приемлемая.
- Память не зависит от числа сессий: RSS 2.6 ГиБ на всех прогонах.

### Стресс: сколько сессий выдержит

Прогоны с ускоренной подачей аудио (`--speed 3/6`): 20 сессий × 3 и 10 × 6 —
это эквивалент 60 одновременных говорящих по нагрузке на инференс (фразы
приходят в 3–6 раз чаще), при меньшем числе соединений.

| Прогон | Сессий × скорость | Эквивалент потоков | Фраз | Overflow | Задержка p50 / p95 / max, с | Инференс p50 / p95, с | GPU avg / max | CPU avg / max |
|---|---|---|---|---|---|---|---|---|
| `ws_ctc_40_x1` | 40 × 1 | 40 | 1160 | 0 | 0.117 / 0.169 / 0.374 | 0.037 / 0.071 | 7 % / 19 % | 364 % / 595 % |
| `ws_ctc_20_x3` | 20 × 3 | 60 | 580 | 0 | 0.068 / 0.124 / 0.207 | 0.039 / 0.092 | 9 % / 22 % | 499 % / 864 % |
| `ws_ctc_10_x6` | 10 × 6 | 60 | 290 | 0 | 0.054 / 0.093 / 0.139 | 0.037 / 0.074 | 11 % / 24 % | 505 % / 769 % |

(В ускоренных прогонах задержка «конец аудио → текст» измеряется в ускоренном
времени, поэтому абсолютные значения меньше; смотреть надо на инференс и
отсутствие overflow.)

Вывод: **40 реальных сессий и эквивалент 60 потоков — без единой потери фразы**,
инференс фразы остаётся 37–39 мс (p95 до 0.09 с — это очередь), GPU занята
на 7–11 % в среднем и до 24 % в пиках. CPU при 60 эквивалентных потоках —
5 ядер из 20. Экстраполяция: одна GPU-модель под одним локом выдержит порядка
**200+ одновременных говорящих** по GPU (25 фраз/с × 40 мс), CPU кончится
раньше — около **150 сессий** при 0.1 ядра на сессию, если не вынести VAD и
фичи в отдельные процессы. Для заявленных 2–3 пользователей это запас на два
порядка.


## 3. Whisper large-v3-turbo (whisper.cpp, CUDA)

Окна псевдо-стриминга вырезаны из того же клипа. `whisper-cli` с прогретой
моделью (тайминги самого whisper.cpp; `load time` ~0.4 с — это загрузка весов
при старте процесса, в сервере она разовая):

| Конфигурация | Энкодер | Декод | Итого без загрузки |
|---|---|---|---|
| окно 5 с, greedy | 174–181 мс | 10–12 мс | ~0.19 с |
| окно 10 с, greedy | 172–177 мс | 12 мс | ~0.19 с |
| окно 15 с, greedy | 177–179 мс | 12 мс | ~0.19 с |
| окно 30 с, greedy | 174–182 мс | 11 мс | ~0.19 с |
| окно 10 с, beam 5 | 175–178 мс | 47–50 мс | ~0.23 с |
| окно 10 с, `-ac 500` | 105 мс | 19 мс | (аномально долгий total 1.9 с — не использовать) |

Энкодер whisper.cpp всегда паддит вход до 30 с, поэтому длина окна на
стоимость почти не влияет — платим ~175 мс за любое окно. `whisper-server`,
параллельные POST окна 10 с (сервер обрабатывает по очереди):

| Параллельных запросов | Суммарное время | На запрос |
|---|---|---|
| 1 | 0.26 с | 0.24 с (включая прогрев) |
| 3 | 0.37 с | ~0.12 с |
| 6 | 0.73 с | ~0.12 с |

То есть **~8 окон в секунду** последовательно. Для псевдо-стриминга с тремя
пользователями и тактом 0.5 с нужно 6 окон/с — укладывается; с тактом 1 с —
двукратный запас. Память: 2.4 ГиБ (веса 1.6 ГБ + контекст), RSS 0.3 ГиБ.

Сравнение с GigaAM на той же GPU: фраза 5 с у GigaAM — 35 мс, у Whisper — 120–190
мс; в 4–5 раз дороже, но всё ещё далеко от предела.

Качество текста (окно 30 с, greedy, без промпта): «О, жги. О, оно хорошо
работает. А, даже не успела что ли показать индикатор?» — совпадает с GigaAM
на этом отрезке; с промптом и beam 5 отличий нет.

### 3.1 faster-whisper (CTranslate2 4.6.0, CUDA) — то же окно 10 с

Сборка CTranslate2 из исходников под sm_120/121 (`benchmark/streaming/Dockerfile.fasterwhisper`),
модель `Systran/faster-whisper-large-v3-turbo`. Батч — окна из **разных мест**
клипа, как от разных пользователей, через `model.encode` + `model.generate`
(то, что `BatchedInferencePipeline` делает внутри). Greedy, если не сказано иное;
p50 из 5 прогонов, GPU свободна.

| compute | Батч | Всего, с | На окно, с | Окон/с |
|---|---|---|---|---|
| float16 | 1 | 0.068 | 0.068 | 14.7 |
| float16 | 3 | 0.276 | 0.092 | 10.9 |
| float16 | 3, beam 5 | 0.148 | 0.050 | 20.2 (выброс, см. ниже) |
| float16 | 6 | 0.450 | 0.077 | 13.0 |
| int8_float16 | 1 | 0.053 | 0.053 | 18.9 |
| int8_float16 | 3 | 0.268 | 0.089 | 11.2 |
| int8_float16 | 3, beam 5 | 0.325 | 0.108 | 9.3 |
| int8_float16 | 6 | 0.393 | 0.066 | 15.3 |

Память: fp16 — 3.5 ГиБ, int8 — 2.7 ГиБ (включая CUDA-контекст). Полный клип
137 с через `BatchedInferencePipeline` (VAD, batch 8, промпт с терминами):
**0.79 с fp16 / 0.64 с int8** (RTF 0.005–0.006) — уровень GigaAM (0.53 с). Текст
корректный: «Проверяем транскрипцию через GigaChat. О, жги. О, оно хорошо
работает…».

Что видно:
- **Окно стоит 0.05–0.09 с** — в 1.5–2 раза дешевле, чем в whisper.cpp
  (0.12 с в сервере, 0.175 с энкодер в cli). 11–15 окон/с против ~8.
- **Батчинг не даёт выигрыша на окно**: 3 и 6 окон стоят столько же за штуку,
  что и одно (даже чуть дороже). Энкодер large-v3-turbo на 30-секундном
  паддинге насыщает 48 SM GB10 уже одним окном — батч тут не масштабирует, в
  отличие от больших GPU. Строка «beam 5 = 0.148 с» — выброс замера (быстрее
  greedy быть не должно), считать её надо как ~0.3 с.
- int8_float16 быстрее fp16 на ~20 % и на 0.8 ГиБ экономнее при том же тексте.

**Рядом с LLM** (gpt-oss:120b генерирует непрерывно, fp16, greedy):

| Батч | Без LLM: на окно, с | С LLM: на окно, с | Окон/с с LLM |
|---|---|---|---|
| 1 | 0.069 | 0.149 | 6.7 |
| 3 | 0.093 | 0.187 | 5.4 |
| 6 | 0.078 | 0.149 | 6.7 |

LLM во время этих прогонов: 35.5 ток/с в среднем (min 26.7) против 44 в
одиночестве — **−20 %**, заметно больше, чем при whisper.cpp (−9 %) и GigaAM
(−1 %): faster-whisper гоняет GPU плотнее. Окно дорожает в 2–2.2 раза, как и у
whisper.cpp, но остаётся 5–7 окон/с.

Вывод: faster-whisper на Spark **работает и предпочтительнее whisper.cpp** —
быстрее, экономнее, Python-API встаёт в сервис напрямую, есть `initial_prompt`
и `hotwords`. Но ожидание «батч спасёт под нагрузкой» не подтвердилось: потолок
одной GB10 для Whisper turbo — порядка 10–15 окон/с в одиночестве и вдвое
меньше рядом с работающей LLM. Для 3 пользователей с тактом 0.5–1 с (3–6
окон/с) этого хватает даже при соседстве.

Грабли сборки и замера — в `docs/SPARK.md` (п. 9–10).

## 4. Соседство с языковой моделью на той же GPU

Замер 2026-09-24, вечер: сервисы STT + непрерывная генерация LLM в `ollama`
(один последовательный запрос за другим, по 400 токенов). Соседний
`faces-and-persons` всё время простаивал (монитор в `faces_activity.csv`).
Две модели: `gpt-oss:120b` (MoE, 64 ГБ на GPU, быстрая) и `qwen3:32b`
(плотная, 31 ГБ, целиком упирается в шину памяти).

| | Без LLM | На фоне gpt-oss:120b | На фоне qwen3:32b |
|---|---|---|---|
| GigaAM, 3 сессии: задержка p50 / p95, с | 0.081 / 0.124 | 0.094 / 0.140 | 0.093 / 0.140 |
| GigaAM: инференс фразы p50 / p95, с | 0.018 / 0.021 | 0.029 / 0.052 | 0.028 / 0.050 |
| Whisper turbo: 3 окна по 10 с параллельно, с | 0.37 | 0.76 | 0.90 |
| LLM, ток/с: одна | 44.1 | 10.3 |
| LLM, ток/с: во время GigaAM (3 сессии) | 43.6 (−1 %) | 10.2 (−1 %) |
| LLM, ток/с: во время Whisper | 40.1 (−9 %) | 9.8 (−5 %) |
| Свободная память при загруженной LLM | 105 ГиБ | 36 ГиБ | 73 ГиБ |

Что видно:
- **GigaAM и LLM друг другу почти не мешают.** Инференс фразы растёт с 18 до
  ~29 мс, задержка для пользователя — на ~10 мс; LLM теряет 1 % скорости.
  Плотная и MoE-модель дают одинаковый эффект.
- **Whisper страдает заметнее**: три окна за 0.76–0.90 с вместо 0.37 (в 2–2.4
  раза медленнее), потому что энкодер Whisper тяжёлый и делит шину памяти с
  генерацией токенов. Это по-прежнему ~3–4 окна/с — для трёх пользователей с
  тактом 1 с хватает, с тактом 0.5 с уже впритык. LLM при этом теряет 5–9 %.
- Память: gpt-oss:120b + STT (обе модели GigaAM + whisper-server) оставляют
  36 ГиБ свободными; с плотной 32B — 73 ГиБ.

Вывод для продукта: на одном GB10 голосовой ввод и большая LLM уживаются.
С GigaAM пользователь разницы не заметит; с Whisper запас по скорости
сокращается вдвое, и такт псевдо-стриминга стоит держать около 1 с.

## 5. Что это значит для продукта

| Вопрос | Ответ по замерам |
|---|---|
| Задержка живой диктовки (GigaAM) | ~0.1 с после конца фразы + 0.5 с ожидания паузы ≈ **0.6–0.7 с** «замолчал → текст»; с партиалами (план, этап C) первый текст ожидается через ~0.5 с после начала речи |
| Задержка псевдо-стриминга Whisper | окно 10 с за 0.12–0.24 с → такт 0.5–1 с реалистичен, коммит слова через ~1–2 с |
| Память | GigaAM 4 ГиБ (обе модели), Whisper 2.4 ГиБ; вместе < 7 ГиБ из 121 |
| GPU | почти свободна: GigaAM 0–4 % при 20 сессиях; Whisper ~15 % на пользователя при такте 0.5 с |
| Рядом с LLM | GigaAM: +10 мс к задержке, LLM −1 %; Whisper: окна в 2–2.4 раза медленнее, LLM −9 % (whisper.cpp) / −20 % (faster-whisper) (§3.1, §4) |
| Сколько сессий | GigaAM: 20 без деградации; ограничитель CPU ≈ 0.1 ядра/сессия. Whisper: 3 пользователя с запасом ×2, ~6–8 — предел одного сервера при такте 1 с |
| Как растёт нагрузка | линейно по CPU с числом сессий; GPU-очередь не образуется до десятков сессий |

Оговорки: один клип чистой речи, синтетическая нагрузка (все сессии — одна
запись со сдвигом), whisper.cpp без батчинга (CTranslate2/vLLM могли бы дать
больше). Числа — потолок для «нормальной» речи; на шумной и с длинными фразами
инференс дольше, но пропорции сохранятся.

## Приложение. Та же матрица на GeForce GTX 1050 Ti (Development Box, CUDA 12)

Дата: 2026-09-30. Хост: ThinkPad X1 Extreme, i7-8750H (6 ядер), **GTX 1050 Ti
4 ГБ** (Pascal, compute capability 6.1), драйвер 535, NVIDIA Container Toolkit.

Что видно:
- Для **1–10 пользователей в фразовом режиме** карта бокса даёт то же ощущение,
  что Spark: текст через ~0.1–0.15 с после конца фразы. Ускорение против CPU
  бокса — в 3–6 раз по инференсу, и главное — инференс уходит с шести ядер
  ноутбука.
- Потолок — **CPU, а не GPU**: на 20 сессиях GPU занята на 14 %, но шесть ядер
  (VAD, фичи, WebSocket на каждую сессию плюс RNNT-декодер) заканчиваются, и
  очередь растёт до секунд. На Spark те же 20 сессий шли без деградации, потому
  что там 20 ядер.
- **RNNT здесь невыгоден**: его покадровый декодер живёт на CPU и стоит 0.24 с
  на фразу, в 3.5 раза дороже CTC; на 10 сессиях уже деградация. На этом боксе —
  только `v3_e2e_ctc`.
- **Партиалы (этап C плана)**: окно 10 с у CTC — ~0.15–0.2 с (по инференсу
  0.07 с на фразу 5 с), такт 0.4 с для 1–2 пользователей укладывается. На CPU
  бокса то же окно стоило ~0.9 с, то есть партиалы там были невозможны — вот
  что реально даёт 4 ГБ старой видеокарты.
- Память: 2.1 ГБ VRAM на обе модели, RSS 1.5–1.9 ГиБ.
